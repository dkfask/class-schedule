# 智程排课产品设计需求

> 文档类型：产品设计层需求草案
>
> 文档状态：候选需求，待真实学校访谈和业务负责人确认
>
> 适用阶段：单校付费试点前的产品完善
>
> 更新时间：2026-09-08

## 1. 文档目的

当前系统已经具备“学期数据导入、教学计划、规则配置、异步求解、候选版本、人工调整、发布和课表查询”的技术闭环。本文件讨论下一步从产品使用角度需要补齐的能力，重点解决以下问题：

1. 排课员打开系统后，能否明确知道当前阶段、阻塞原因和下一步动作。
2. 自动排课结果是否足够可解释，排课员是否敢于采用并发布。
3. 导入、配置、求解、人工调整和发布是否形成可重复的学校业务流程。
4. 学校负责人、排课员和只读用户之间是否有清晰的协作与交付边界。
5. 一次试点完成后，下一学期能否复用数据、规则、版本和交付经验。

本文只定义产品目标、用户体验、功能边界和验收方向，不直接规定数据库表、接口实现或具体算法。

## 2. 当前产品基线

### 2.1 已有能力

以下能力视为当前产品基线，不重复列为新需求：

- 单校、单学期排课；
- 教师、行政班、课程、教室和教学需求维护；
- Excel 模板导入、预览、确认和错误定位；
- 教学需求的课时、连堂、固定节次、活动组等信息进入求解输入；
- 教师、班级和教室等硬约束校验；
- 异步求解任务、进度、取消、重试和截止时间；
- 候选版本、版本复制、人工调整、交换、锁定、撤销和重做；
- 班级、教师和教室三维课表视图；
- 发布门禁、已发布版本保护、导出和打印入口；
- 排课员与只读用户的基础访问边界；
- AI 辅助入口，但 AI 输出不作为排课事实或发布依据。

### 2.2 产品判断

当前系统更像一个“排课引擎工作台”，下一阶段应优先变成一个“可交付的学校排课产品”。核心价值不是再增加更多规则名称，而是让业务人员能够：

> 准确准备数据，理解约束，得到候选方案，安全调整，完成发布，并在出现问题时找到责任和依据。

## 3. 产品目标与非目标

### 3.1 产品目标

#### G1：降低首次使用门槛

第一次使用时，排课员不需要阅读技术文档，也能沿着系统引导完成学期准备、数据检查和首次求解。

#### G2：让“不可排”和“不可发布”可解释

系统必须告诉用户是哪条数据、哪类规则、哪个资源导致阻塞，并区分可修复的数据问题、规则冲突和求解尚未完成。

#### G3：让人工调整可控、可回退

用户在调整课表前知道影响范围，调整后可以确认、撤销、重做并查看操作记录，避免一次操作破坏整张课表。

#### G4：形成学校可交付的发布流程

发布不是一个单独按钮，而是经过数据新鲜度、任务完整性、硬约束、人工确认和版本说明的正式业务节点。

#### G5：为下一学期和商业试点积累可复用资产

学校的作息、基础数据、规则模板、版本、问题清单和验收结果应能够复用或追溯，降低重复实施成本。

### 3.2 明确非目标

本阶段不纳入以下产品承诺：

- 完整教务平台，包括成绩、考勤、收费、家长端和学生个人选课；
- 复杂走班、分层教学、跨校区、考试排程和实训设备排课；
- 在没有真实数据和规则确认的情况下承诺全局最优；
- 立即建设多租户 SaaS、在线支付、套餐和自动计费；
- 让 AI 直接生成、修改或自动发布排课事实；
- 以移动端替代复杂的桌面排课和人工调整工作台。

## 4. 用户与角色

| 角色 | 主要目标 | 可以做什么 | 本阶段不应默认拥有的能力 |
| --- | --- | --- | --- |
| 排课员 | 准备数据、生成并调整课表、完成发布 | 编辑主数据和规则，提交求解，调整、锁定、发布和导出 | 修改已发布版本的历史事实 |
| 学校业务负责人 | 确认规则和最终课表 | 查看准备度、审核候选版本、查看差异和发布记录 | 默认修改系统配置或绕过发布门禁 |
| 教师/管理人员 | 查看已发布课表 | 按教师、班级、教室查询和打印已发布课表 | 查看内部草稿、规则内部配置和未发布版本 |
| 实施/支持人员 | 协助导入、配置和问题定位 | 在授权范围内查看导入批次、求解任务、审计和问题清单 | 无授权访问学校业务数据 |
| 平台管理员（后续） | 管理学校、用户和服务 | 组织、成员、权限、服务状态和审计管理 | 直接改变学校课表业务事实 |

### 4.1 当前角色与候选角色的关系

当前代码主要提供排课员和只读用户边界。业务负责人、实施人员和平台管理员属于产品设计候选角色，是否独立成角色需要在真实试点前确认，不应仅凭当前技术角色推导出最终组织权限。

## 5. 核心用户流程

### 5.1 首次建学期流程

```text
选择学期
  -> 查看准备度
  -> 下载或选择模板
  -> 导入并预览
  -> 修复数据问题
  -> 确认导入
  -> 配置规则
  -> 运行可行性预检
  -> 提交首次求解
```

设计要求：

- 每个阶段只呈现当前需要完成的主要动作；
- 阻塞项、警告项和已完成项必须分组显示；
- 可选数据缺失不能被误显示为失败，明确提交的停用、解绑等动作必须有影响说明；
- 用户离开页面或切换学期时，不应丢失已填写但未提交的内容；
- 任意阶段都可回到问题来源，而不是只显示“数据不合法”。

### 5.2 自动排课流程

```text
检查可求解
  -> 提交求解任务
  -> 查看排队/运行进度
  -> 查看候选结果
  -> 查看未排任务与扣分解释
  -> 选择继续调整或重新求解
```

设计要求：

- 求解中显示任务状态、进度、开始时间、预计状态说明和取消入口；
- 状态必须区分“等待执行、正在求解、已完成、失败、已取消、已超过截止时间”；
- 完成后同时显示任务完整性、硬约束、软约束、未排任务和可发布状态；
- 无解或结果不可发布时，页面仍然是一个可继续工作的结果页，而不是只显示错误弹窗；
- 重新求解前明确哪些人工调整会被保留、哪些会被覆盖。

### 5.3 人工调整流程

```text
选择课次
  -> 查看当前安排
  -> 选择目标节次/教室
  -> 查看调整预览
  -> 阅读冲突与受影响对象
  -> 确认调整
  -> 记录版本变化
  -> 必要时撤销或重做
```

设计要求：

- 调整前优先展示冲突结果，不让用户通过试错才能知道是否可行；
- 对冲突分为硬阻塞、软约束损失、锁定冲突和信息提醒；
- 说明受影响的教师、班级、教室、活动组和其他课次；
- 调整确认后明确提示版本已经变为待检查/草稿状态；
- 新命令产生后，失效的重做操作不应继续显示为可用；
- 用户在离开版本页面前，若有待确认的操作或结果刷新异常，应看到明确提示。

### 5.4 发布与分发流程

```text
候选版本
  -> 发布检查清单
  -> 查看未通过项
  -> 填写版本说明
  -> 业务负责人确认
  -> 发布新版本
  -> 查看发布结果
  -> 查询、打印、导出
```

设计要求：

- 发布前显示“为什么可以发布”和“还有哪些非阻塞提醒”；
- 已发布版本必须显示学期、版本标识、发布时间、发布人和版本说明；
- 已发布版本只能通过创建新版本的方式修正，不能直接覆盖历史发布结果；
- 发布失败时保留候选版本，不让用户重新导入或重新求解才能继续；
- 只读用户只看到已发布版本，并能快速切换班级、教师和教室视图；
- 导出文件和打印页面必须带学期、版本标识和生成时间，避免拿错版本。

## 6. 功能需求

优先级定义：

- **P0**：影响首个学校试点能否顺利完成，进入下一产品迭代；
- **P1**：影响持续使用、交付效率和续费，完成首个试点后排期；
- **P2**：规模化、生态和商业化能力，满足商业闸门后再立项。

### P0：试点可交付闭环

#### PD-P0-01 学期排课总览与准备度

**目标**：让排课员和业务负责人一眼知道当前学期处于哪个阶段、还缺什么、谁可以处理。

**需求**：

- 展示学期上下文、当前版本、当前流程阶段和最后更新时间；
- 展示基础数据、教学计划、规则、求解、人工调整、发布六个阶段的状态；
- 每个阶段提供完成数、阻塞数、警告数和进入处理页面的入口；
- 提供单一“下一步建议”，避免同一页面出现多个同等优先级的主按钮；
- 对数据变更、规则变更、输入快照过期、任务失败和版本待复核提供明确提醒；
- 展示最近导入、最近求解、最近调整和最近发布活动。

**验收方向**：首次进入一个未配置学期时，用户能明确看到“先完成什么”；进入一个已存在候选版本的学期时，用户能明确看到“是否可以继续调整或发布”。

#### PD-P0-02 数据导入与数据健康向导

**目标**：把 Excel 导入从一次性动作变成可恢复的数据准备流程。

**需求**：

- 提供“模板下载—文件选择—结构检查—数据预览—错误修复—确认导入”的步骤条；
- 按 Sheet、行、列、业务对象和严重程度归类错误；
- 对重复编码、无效引用、已停用引用、时间格式错误、课时不一致等问题给出可读解释；
- 显示本次导入将新增、更新、停用、解绑和保持不变的记录数量；
- 可选 Sheet 或空数据不应被误判为删除已有配置；
- 支持保留上一次预览结果，修复文件后重新预览，不重复确认旧批次；
- 确认后显示导入批次、文件摘要、影响范围和操作人。

**产品边界**：系统可以解释结构和业务一致性问题，但不能替学校自动猜测教师、班级或课程的真实对应关系。

#### PD-P0-03 规则中心与规则解释

**目标**：让排课员知道规则会影响什么，以及规则为什么阻止发布。

**需求**：

- 将规则按时间、资源、活动组、分布、偏好和发布门禁分类；
- 每条规则显示名称、作用对象、作用学期、强度、权重、当前状态和来源；
- 区分硬阻塞、软约束损失、业务偏好和仅供提示的规则；
- 对每条规则说明参数含义、影响对象和生效范围；
- 对可能重复、冲突或覆盖的规则给出配置提示；
- 提供“仅查看当前学期生效规则”的筛选入口；
- 在冲突报告中反向链接到产生问题的规则和资源。

**产品边界**：规则目录可以扩展，但没有经过业务确认的规则不能仅因为名称看起来相似就自动启用。

#### PD-P0-04 求解任务与候选方案工作流

**目标**：把求解结果从技术状态转成业务可判断的候选方案。

**需求**：

- 任务卡显示提交人、提交时间、输入学期、输入版本/快照、当前状态、进度和取消入口；
- 对失败结果显示失败类别、是否可重试、建议的下一步和相关数据入口；
- 对完成结果显示总教学任务数、已安排数、未安排数、硬约束、软约束和可发布状态；
- 未排任务按原因、教师、班级、课程和活动组分组；
- 冲突报告支持从规则到资源、从资源到课次的双向查看；
- 允许业务用户比较两个候选版本的总体指标和具体课次变化；
- 重新求解前显示“将保留/将重置”的锁定、手工调整和规则影响。

**AI 辅助要求**：AI 只能提供候选解释、问题摘要或调整建议；每条建议必须指向可核验的课次、资源和规则，用户确认前不得写入课表。

#### PD-P0-05 安全人工调整工作台

**目标**：让排课员能高效处理少量例外，而不是重新从头排课。

**需求**：

- 课表支持班级、教师、教室三种视图，并能保持当前筛选条件；
- 选中课次后展示课程、班级、教师、教室、节次、活动组、固定状态和来源；
- 目标位置提供可用节次和教室列表，并优先显示无冲突选项；
- 调整预览显示硬冲突、软约束变化、锁定冲突和受影响课次；
- 支持移动、交换、锁定、解锁、撤销和重做；
- 版本被其他用户更新后，当前页面必须提示刷新或重新加载，不得静默覆盖；
- 调整操作显示命令时间、操作人、变化前后值和原因备注入口。

#### PD-P0-06 发布检查清单与发布记录

**目标**：把发布变成可审查、可解释、可追责的正式动作。

**发布前检查项**：

- 所有目标教学任务已分配，且不存在缺失、重复、额外或课时不一致；
- 硬约束为零，独立校验通过；
- 输入数据和规则快照未过期；
- 固定课和锁定课未被非法改变；
- 必要的人工确认和版本说明已完成；
- 导出和打印所需的基本信息完整。

**需求**：

- 检查项分为阻塞项、警告项和已通过项；
- 阻塞项必须能进入问题详情；
- 发布确认需显示版本标识、适用学期、课次数量和发布人；
- 发布成功后生成不可变的发布记录；
- 对已发布版本提供“基于此版本创建修订版”的入口，而不是编辑已发布版本；
- 发布历史按时间倒序展示，并支持查看差异、导出和归档状态。

#### PD-P0-07 已发布课表的查询与分发

**目标**：让教师和管理人员无需理解排课过程，也能快速获得正确课表。

**需求**：

- 默认打开当前学期最新已发布版本，并明确显示版本信息；
- 支持按班级、教师、教室筛选和搜索；
- 支持周视图、打印视图、Excel 导出和 PDF 导出；
- 在打印和导出文件中显示学校/学期/版本/生成时间等识别信息；
- 空课表、无教室、缺少数据和导出失败时提供可理解的空态或错误说明；
- 只读用户不能通过 URL、版本号或导出参数读取草稿和内部候选版本。

#### PD-P0-08 审计与问题定位入口

**目标**：试点交付和售后支持时，能够还原一次业务变化。

**需求**：

- 对导入、规则变更、求解提交、取消、调整、锁定、发布、归档和权限变化记录操作人、时间、对象和结果；
- 审计记录支持按学期、版本、用户、操作类型和时间筛选；
- 业务人员看到可读摘要，支持人员可查看更完整的输入/输出摘要；
- 失败任务和导入批次可以关联到问题记录或交付清单；
- 审计记录本身不可被普通用户修改或删除。

### P1：持续使用与交付效率

#### PD-P1-01 学校组织与协作权限

- 引入学校、校区、年级、班级等组织上下文；
- 支持多个排课员协作，并明确谁可以编辑、谁可以审核、谁可以发布；
- 业务负责人可只读查看准备度、候选方案和发布检查清单；
- 权限错误应说明“没有权限”与“对象不存在”的区别策略；
- 所有对象、导入批次、版本、任务和审计记录都要有清晰的学校归属。

该需求必须在多校 SaaS 之前完成组织与权限模型设计，但不等于已经具备多租户 SaaS 能力。

#### PD-P1-02 站内通知与待办

- 导入完成、导入失败、求解完成、求解失败、需要处理冲突、版本被更新、发布完成时生成通知；
- 通知关联具体学期、版本、任务或问题；
- 支持“待处理、已读、已完成”状态；
- 首期优先建设站内通知，邮件、企业微信和短信作为后续渠道；
- 用户可以关闭低价值提醒，但不能关闭安全、发布失败和权限异常提醒。

#### PD-P1-03 学期复制与数据复用

- 支持从上一学期复制作息、主数据、规则模板和教学计划草稿；
- 复制前显示会复制、不会复制和需要重新确认的内容；
- 教师、班级、课程、教室变化需要提供映射和未匹配清单；
- 不复制上一学期的已发布事实、历史审计和已完成求解任务；
- 新学期必须重新执行数据健康检查和发布门禁。

#### PD-P1-04 规则模板与交付方案

- 支持保存学校级规则模板和试点交付配置；
- 模板有版本、适用学期、维护人和变更说明；
- 模板应用前显示将新增、修改和失效的规则；
- 将复杂规则归类为“已支持、可配置、需实施服务、暂不支持”；
- 规则模板不能绕过当前学期的数据准备和可行性检查。

#### PD-P1-05 交付数据与业务复盘

- 记录从导入到发布的历时、失败原因、人工调整次数和支持介入次数；
- 允许实施人员填写规则适配、遗留问题和学校反馈；
- 按学期生成试点复盘摘要；
- 区分产品指标、算法指标和实施服务指标，避免把算法分数当作客户价值的唯一指标。

#### PD-P1-06 问题与反馈中心

- 用户可以从导入错误、冲突、求解任务和发布记录直接创建问题；
- 问题包含学期、版本、对象、截图/导出文件引用、描述、优先级和处理状态；
- 支持人员可以标记“数据问题、规则不支持、产品缺陷、操作问题、待确认”；
- 关闭问题时保留处理结论和验证依据。

### P2：规模化和生态能力

以下能力先保留产品方向，不进入单校试点承诺：

- 统一身份认证和学校门户集成；
- 轻量移动端/小程序，只承载通知、查询、审核和发布结果查看；
- 教务系统数据接口和定时同步；
- 多校、多组织和租户隔离；
- 订阅、套餐、配额、支付、账单和续费；
- 跨校区、高校复杂选课、考试和设备排课；
- 面向学校集团的运营分析。

进入 P2 前必须满足 `docs/commercialization-plan.md` 第 8 节的多校 SaaS 闸门，不能因为已有用户登录、owner 或基础角色就直接定义为多租户能力。

## 7. 页面与信息架构建议

当前导航已经按“准备—规则—交付”组织。建议保留该主线，同时补一个以任务为中心的总览入口。

### 7.1 推荐导航

```text
当前学期
  ├─ 学期总览（新增，默认入口）
  ├─ 基础数据
  ├─ 数据导入
  ├─ 教学计划
  ├─ 规则中心
  ├─ 排课工作台
  ├─ 版本与发布
  ├─ 已发布课表
  └─ 操作与问题（P0/P1，按实施阶段决定是否合并）
```

### 7.2 页面设计重点

| 页面 | 首要问题 | 必须优先展示 |
| --- | --- | --- |
| 学期总览 | 我现在该做什么 | 当前阶段、下一步、阻塞项、版本和最近活动 |
| 数据导入 | 数据是否可信 | 导入影响、错误分组、可选项语义、批次状态 |
| 教学计划 | 任务是否完整 | 班级/课程/教师/课时、缺失和重复、学期范围 |
| 规则中心 | 规则如何生效 | 规则强度、作用对象、参数、冲突和来源 |
| 排课工作台 | 哪里需要人工处理 | 未排池、课表网格、资源过滤、调整预览和受影响项 |
| 版本与发布 | 这个版本能否交付 | 差异、快照、门禁、检查清单、确认和审计 |
| 已发布课表 | 如何拿到正确课表 | 版本识别、三维查询、打印和导出 |
| 操作与问题 | 发生了什么 | 时间线、责任人、关联对象、处理状态和结论 |

### 7.3 交互原则

- 一个页面只保留一个主要下一步动作，危险动作使用明确的二次确认；
- 技术状态要翻译成业务语言，接口错误码可以在详情中保留但不作为唯一文案；
- 所有空态都要说明是“暂无数据、尚未配置、处理中、无结果”中的哪一种；
- 列表、课表和详情之间保持上下文，返回后保留学期、筛选和视图；
- 重要动作结果使用页面内反馈和状态刷新，不依赖短暂弹窗；
- 不隐藏失败原因，也不把软约束警告显示成硬失败；
- 发布、归档、删除、停用、重新求解等不可逆或有范围影响的动作显示影响范围。

## 8. 关键状态模型

### 8.1 产品层版本状态

以下是面向用户的建议标签，技术状态应映射到这些业务含义：

```text
未开始
  -> 配置中
  -> 待求解
  -> 求解中
  -> 候选待处理
  -> 待发布检查
  -> 已发布
  -> 已归档
```

异常分支：

```text
求解中 -> 已取消
求解中 -> 求解失败
候选待处理 -> 数据已过期
待发布检查 -> 发布被阻塞
已发布 -> 创建修订版 -> 配置中
```

### 8.2 状态设计规则

- “候选”不等于“可发布”；
- “求解完成”不等于“所有任务已安排”；
- “无硬冲突”不等于“业务负责人已确认”；
- 已发布版本不能回到草稿状态，修正必须创建新的版本；
- 输入数据或规则变化后，旧候选版本必须显示过期原因；
- 取消、失败和超时必须保留任务结果摘要与下一步建议。

## 10. 需求优先级与落地顺序

建议按以下顺序推进：

### 第 1 阶段：先让首个试点能独立完成

1. 学期总览与准备度；
2. 数据导入与数据健康向导；
3. 规则解释和冲突定位；
4. 求解结果与未排原因；
5. 人工调整的预览、影响范围和版本反馈；
6. 发布检查清单、发布记录和已发布分发；
7. 导入、求解、调整、发布的审计入口。

### 第 2 阶段：降低每学期重复交付成本

1. 学期复制和数据映射；
2. 规则模板和交付方案；
3. 多人协作、审核和权限；
4. 站内通知和待办；
5. 问题中心和试点复盘。

### 第 3 阶段：有证据后再规模化

1. 轻量移动端查看和审核；
2. 统一身份和教务系统集成；
3. 多校组织/租户；
4. 套餐、配额、支付和账单；
5. 集团级数据分析。

## 11. 首个试点的产品验收门槛

以下不是自动化测试用例，而是产品验收的业务判断标准：

- 排课员能够在没有额外技术说明的情况下完成一次完整导入、预检、求解、调整、发布和导出；
- 导入问题可以回到具体 Sheet、行、列或业务对象；
- 求解失败或不可行时，业务人员可以理解原因并知道下一步处理方式；
- 至少一名非排课员用户能够只查看已发布版本，并完成班级/教师/教室课表获取；
- 发布前可以清楚证明任务完整、硬约束为零、数据未过期且版本已确认；
- 发布后可以通过版本标识、时间、操作人和审计记录还原发布事实；
- 对真实学校数据完成中文浏览器、打印/PDF、主要桌面分辨率和导出文件验收；
- 试点期间记录数据清洗、规则配置、支持和人工调整成本，为商业报价复盘提供依据。

## 12. 待确认事项与下一步

这份文档目前是产品设计候选基线，不代表所有 P0/P1 项目已经获得开发授权。进入开发前，应由学校业务负责人或项目负责人确认：

1. 首个试点学校的角色和发布责任人；
2. 真实数据规模、规则清单和兼容性范围；
3. 求解等待时间、通知渠道和数据留存要求；
4. P0 需求的最终取舍和验收样例；
5. 哪些能力属于标准产品，哪些属于实施服务或单独报价。

用户裁决后，应把结论补回本文档第 9 节 `open_questions`，再进入详细交互稿、接口契约和开发排期。
