# 独立中小学排课系统开发计划

## 1. 文档状态

- 项目类型：独立 Web 排课系统
- 目标学校：中小学
- 第一阶段：可试用 MVP
- 使用方式：排课员编辑，教师和管理人员只读查看已发布课表
- 工作区：`/Users/a1234/Documents/class schedule`
- 计划形成日期：2026-08-23

本文档用于确定产品范围、技术路线、开源项目借鉴边界、实施阶段和验收标准。第一版不建设完整教务平台。

## 2. 建设目标

从零开发一个单校使用的独立排课系统，完成以下业务闭环：

```text
选择学期
  -> 导入或维护基础数据
  -> 编制教学计划
  -> 配置排课约束
  -> 数据可行性预检
  -> 自动生成候选课表
  -> 人工调整和锁定
  -> 完整冲突校验
  -> 发布课表版本
  -> 查询、打印和导出
```

系统的首要质量目标是：

1. 所有已发布课表不存在教师、班级和教室硬冲突。
2. 所有教学任务均已分配，不允许静默漏排。
3. 无解时明确返回不可发布状态和未排原因，不能放宽硬约束后显示成功。
4. 自动排课结果可以人工调整、锁定和局部重排。
5. 每次导入、求解、调整和发布均可追溯。

## 4. 开源项目借鉴边界

采用“洁净室式业务借鉴 + 宽松许可证依赖”。不把多个旧项目的代码直接拼装成新系统。

### 4.1 Timefold Solver Community

用途：实际排课求解器。

可以采用：

- Planning Entity、Planning Variable 和 Problem Fact 模型
- Constraint Streams
- Hard/Medium/Soft 分数
- 固定实体和锁定重排
- 异步求解、状态查询和终止
- ConstraintVerifier 约束单测
- 官方 school timetabling quickstart 的工程结构

边界：

- 使用 Apache-2.0 社区版
- 业务数据库实体不直接加求解器注解
- 规划模型作为独立 DTO
- 不把商业版能力作为首期架构前提

### 4.2 OpenEDU ICS

只借鉴业务流程：

```text
排课任务 -> 基础数据 -> 规则 -> 预排 -> 自动排课 -> 手调 -> 查询与发布
```

可以借鉴：

- K-12 排课模块划分
- 全校、课程、班级和教师时间限制
- 合班和预排流程
- 班级与教师并排的手调思路
- 冲突提示和多维课表查询

不可复制：

- GPLv3 Java/Vue 源码
- 数据库脚本和表结构
- 页面代码、图片和文案
- 字符串化主数据
- 通用 JSON 规则表
- 位图随机贪心和遗传算法实现

### 4.3 FET

只借鉴：

- Activity/Subactivity 概念
- 时间约束和空间约束分类
- 连堂、同步、分布、空档和教室约束词典
- CSV/XML/HTML 导入导出思想

不可采用：

- AGPL 求解代码
- Qt 桌面 UI
- FET XML 作为系统内部主数据模型
- 将 FET 直接嵌入闭源 Web 服务

### 4.4 UniTime

- 高校 Offering、Config、Subpart、Class 全套层级
- 学生选课、考试和活动管理
- GWT/Struts 等旧架构

### 4.5 CourseArragement

可以参考：

- Excel 模板导入

### 4.6 台湾小学排课项目

## 5. 技术架构

### 5.1 默认技术栈

- 后端：Java 17
- 框架：Spring Boot
- 求解器：Timefold Solver Community 稳定版
- 数据库：PostgreSQL
- 数据库迁移：Flyway
- Excel：Apache POI
- 前端：Vue 3、TypeScript、Vite
- 状态管理：Pinia
- 路由：Vue Router
- UI：Element Plus
- 图标：Lucide
- 后端测试：JUnit 5、ConstraintVerifier、Testcontainers
- 前端测试：Vitest
- 浏览器验收：Playwright
- 本地基础设施：Docker Compose

工程初始化阶段先验证 Java、Spring Boot 与 Timefold 稳定版兼容组合，再锁定 BOM 和版本，不直接拼接各项目的最新版本。

### 5.2 部署结构

```text
Vue Web
   |
Spring Boot API
   |
PostgreSQL
   |
持久化 Solve Job 队列 / Outbox
   |
Spring Worker + Timefold Solver
```

采用一个代码库和模块化单体：

- API 负责事务、权限、版本、校验和任务提交
- Worker 负责 CPU 密集型求解
- API 和 Worker 使用不同 Spring Profile 和部署进程
- PostgreSQL 是事实源
- 首期使用 PostgreSQL Job Table 和 `FOR UPDATE SKIP LOCKED`
- 未来规模扩大后再评估 RabbitMQ 或 Kafka

禁止在同步 HTTP 请求中等待长时间求解完成。

## 7. 核心数据模型

业务数据库模型与 Timefold 规划模型必须分离。数据库实体转换为不可变 `PlanningProblem`，求解结果经独立校验后写回。

### 7.1 学期和时间

- `AcademicTerm`
- `CalendarDay`
- `PeriodTemplate`
- `Timeslot`

### 7.2 组织与资源

- `Grade`
- `StudentGroup`
- `Teacher`
- `Subject`
- `Room`
- `RoomFeature`
- `TeacherAvailability`
- `RoomAvailability`

首期 `StudentGroup` 主要表达行政班，但模型保留教学班扩展能力。

### 7.3 教学需求

- `TeachingRequirement`
- `LessonOccurrence`
- `ActivityGroup`
- `ResourceRequirement`

`TeachingRequirement` 表达某学期、某班级、某课程的周课时和授课关系。

`LessonOccurrence` 是主要待排任务。连续两节课建模为一个占用多个连续节次的任务，而不是两个可以分开的独立任务。

`ActivityGroup` 表达：

- 合班
- 同步
- 连堂
- 先后关系
- 未来的拆班和分层

### 7.4 约束

- `ConstraintDefinition`
- `ConstraintInstance`
- `ConstraintProfileVersion`

### 7.5 排课和版本

- `ScheduleScenario`
- `SolveJob`
- `ScheduleVersion`
- `Assignment`
- `ScoreBreakdown`
- `PublishedSnapshot`
- `AdjustmentCommand`
- `AuditEvent`

`Assignment` 至少包含：

- occurrence
- startTimeslot
- room
- 来源：`SOLVER`、`MANUAL`、`IMPORT`
- 是否锁定
- 调整人
- 调整原因

### 7.6 版本状态

```text
DRAFT -> SOLVING -> CANDIDATE -> PUBLISHED -> ARCHIVED
                    \-> FAILED
```

每次自动排课、Excel 批量导入或人工调整都从父版本派生新版本，不原地覆盖已发布课表。

数据库资源唯一约束必须包含 `schedule_version_id`，例如：

- `(version_id, room_id, timeslot_id)`
- `(version_id, teacher_id, timeslot_id)`
- `(version_id, student_group_id, timeslot_id)`
- `(version_id, lesson_occurrence_id)`

合班、多教师和连续多节占用仍需独立业务校验器进行完整检查。

## 8. 求解器模型

### 8.1 Planning Entity

使用 `LessonOccurrence` 或连续课块作为规划实体。

主要规划变量：

- `startTimeslot`
- `room`

任课教师首期由教学计划确定，不作为规划变量。固定课、已发布课和人工锁定课通过 Pinning 固定。

### 8.2 分数层级

使用 `HardMediumSoftScore`，不使用一个超大整数伪装优先级。

#### Hard

- 教师同一时段不能冲突
- 班级同一时段不能冲突
- 教室同一时段不能冲突
- 教师、班级和教室不可用时间不能排课
- 每个 occurrence 必须分配或明确标记未排
- 连堂必须连续
- 连堂不能跨午休等禁止边界
- 固定课和锁定课不可移动
- 教室容量和特征满足要求
- 合班课的所有班级必须同步

#### Medium

- 同科课次在一周内合理分散
- 教师每日课时上限
- 班级每日课时结构
- 主课尽量安排在指定时段
- 局部重排时尽量减少父版本变动

#### Soft

- 减少教师空档
- 满足教师时段偏好
- 固定教室
- 避免同一班连续出现过多同类课程
- 平衡教师工作负荷

### 8.3 未排任务

允许规划过程中存在显式 `UNASSIGNED` 状态，但给予 Hard 惩罚。这样超约束数据可以返回：

- 最佳不可发布候选
- 未排任务
- 相关资源不足
- 违反的规则

禁止为得到表面完整课表而放宽硬约束。

### 8.4 独立校验器

Timefold 结果不能直接发布。系统需要另一套不依赖 Timefold Constraint Streams 的业务校验器，重新检查：

- 任务数量和课时守恒
- 教师冲突
- 班级冲突
- 教室冲突
- 可用性
- 连堂
- 合班
- 固定和锁定安排
- 教室容量和特征

只有求解器 Hard score 为 0，并且独立校验器通过，才允许发布。

## 9. Excel 设计

### 9.1 模板 Sheet

MASTER_DATA v1 模板固定按以下顺序提供 Sheet，表头使用中文，列顺序不可调整：

- 说明
- 教师：编码、名称、是否启用
- 班级：编码、名称、班级类型、学生人数、是否启用
- 课程：编码、名称、是否启用
- 教室：编码、名称、容量、教室类型、是否启用
- 教学需求：编码、学期编码、班级编码、课程编码、教师编码、每周课时、单次节数、学生人数、固定节次编码、是否启用
- 资源可用性：资源类型、资源编码、学期编码、节次编码、是否可用
- 特征目录：编码、名称、是否启用
- 教室特征：教室编码、特征编码、是否启用
- 教学需求特征：教学需求编码、特征编码、是否启用
- 活动组：编码、名称、活动组类型、学期编码、成员序号、教学需求编码、是否启用

学期和节次仅作为引用校验，不在模板中写入；缺少数据行不会删除已有数据。旧五 Sheet 英文表头仅由 LEGACY 兼容路径处理。模板携带类型、版本和稳定 Schema hash。

### 9.2 导入流程

```text
上传
  -> 文件大小和 ZIP 限额
  -> 保存原文件和 SHA-256
  -> 流式解析到 Staging
  -> 字段语法校验
  -> 跨表语义校验
  -> 错误预览
  -> 用户确认
  -> 单事务提交
```

要求：

- 同时保留稳定 ID 和人类可读 code
- 错误精确到 Sheet、行、列和错误码
- 禁止静默部分成功
- 公式单元格默认拒绝或只读缓存值
- 限制文件大小、Sheet 数、行数、字符串长度和压缩比
- 超大导出使用 SXSSF
- 超大导入使用 SAX/Event Model

## 10. 前端设计

第一屏直接进入排课工作台，不制作营销落地页。

### 10.1 导航

左侧固定导航：

- 学期
- 基础数据
- 教学计划
- 排课规则
- 排课方案
- 已发布课表

顶部：

- 当前学期
- 数据导入状态
- 求解任务状态
- 用户菜单

### 10.2 排课工作台

采用三栏布局：

- 左侧：筛选和未排任务池
- 中间：班级课表网格
- 右侧：教师或教室影响课表

拖动时显示：

- 可放置
- 需要交换
- 违反软约束
- 禁止放置

确认前显示：

- 受影响课程
- 资源冲突
- 规则原因
- 分数变化

班级、教师和教室通过标签页切换。已发布课表只读，修改时必须先创建新草稿版本。

课表网格使用稳定节次尺寸和响应式约束，动态内容不得改变网格布局。工具按钮使用图标和工具提示。

- 全新环境可启动 PostgreSQL
- 后端构建通过
- 前端构建通过
- 最小求解测试通过
- 最小 API 到前端闭环通过

## 阶段 2：主数据、教学计划和 Excel

工作内容：

- 实现学期、节次、教师、班级、课程和教室
- 实现可用性
- 实现教学需求和 occurrence 展开
- 实现 Excel 模板、Staging、校验和确认提交
- 实现数据预检

数据预检至少包括：

- 重复 code
- 缺失引用
- 总课时超过可排容量
- 教师工作量超过可用时间
- 固定课冲突
- 教室容量不足

退出条件：

- 示例学校数据可从 Excel 完整导入
- 错误可定位到 Sheet、行和列
- 已知不可行数据可以在求解前被识别

## 阶段 3：手工排课和版本系统

工作内容：

- 班级、教师和教室课表视图
- 草稿、候选、发布、归档、复制和差异
- 拖动前快速校验
- 提交时完整校验
- 锁定、撤销和操作日志
- 版本级唯一约束和乐观锁

退出条件：

- 不运行自动求解也可以手工创建完整课表
- 零硬冲突课表可以发布
- 冲突课表无法发布
- 已发布课表不会被原地覆盖

## 阶段 4：Timefold 自动排课 MVP

工作内容：

- 建立独立 PlanningProblem DTO
- 建立 Solver Adapter
- 实现 Hard 约束
- 为每条约束建立 ConstraintVerifier 测试
- 实现异步 Job、状态、取消、超时和失败恢复
- 实现候选版本写回
- 实现 Score Breakdown 和未排原因
- 实现固定课、合班、连堂和锁定课

退出条件：

- 可行数据在约定时限内得到 Hard=0 候选
- 不可行数据不显示成功
- 任务可以取消
- 结果可追溯到输入快照、规则版本、求解器版本和随机种子
- 独立校验器验证通过后才可发布

## 阶段 5：质量优化和 MVP 验收

工作内容：

- 实现 Medium 和 Soft 约束
- 实现运行时权重
- 实现锁定后的局部重排
- 实现最小扰动评分
- 实现课表、冲突报告和版本差异导出
- 完成打印样式
- 完成排课员和只读权限
- 完成真实规模数据集和性能基准
- 完成浏览器关键流程测试

退出条件：

排课员可以完成完整闭环：

```text
导入 -> 预检 -> 自动排课 -> 手调 -> 校验 -> 发布 -> 导出
```

### 12.4 黄金数据集

项目内维护：

- `small-feasible`：手工可验证的小型可行数据
- `small-infeasible`：明确不可行的数据
- `over-constrained`：超约束数据

保存预期 Hard score 和关键业务性质，不要求限时求解结果逐行完全相同。

- 乐观锁
- Job 领取
- Outbox

### 12.6 Excel 测试

- 重复 code
- 错误类型
- 日期和数字格式
- 公式
- 超大文件
- 损坏 ZIP
- 压缩炸弹限制

### 12.7 API 和浏览器测试

- 导入和确认

- 取消和失败重试
- 手工移动
- 锁定和重排
- 发布权限

### 12.8 性能基准

- 取消率

- 每条规则耗时

## 13. 发布验收门禁

一个候选版本只有同时满足以下条件才可发布：

1. 全部 LessonOccurrence 已分配。
2. Timefold Hard score 为 0。
3. 独立业务校验器通过。
4. 教师冲突为 0。
5. 班级冲突为 0。
6. 教室冲突为 0。
7. 固定课和锁定课未改变。
8. 连堂、合班和教室要求满足。
9. 输入快照、规则版本和求解器元数据已保存。
10. 发布操作通过事务完成并写入审计日志。

## 14. 关键工程原则

- 不复制 OpenEDU/FET 的 GPL/AGPL 代码。
- 不使用随机贪心或自研遗传算法作为生产核心。
- 不把课程、教师和班级保存为无外键字符串。
- 不把所有规则塞入无类型 JSON 万能表。
- 不让求解器直接修改业务数据库。
- 不在同步 HTTP 请求中运行长时间求解。
- 不原地覆盖已发布课表。
- 不把 Excel 当数据库。
- 不把“生成了结果”当成“可以发布”。
- 不在没有真实基准数据时宣称算法达到生产质量。
- Hard=0 和独立校验同时通过才允许发布。

## 15. 主要风险

### 业务风险

如果没有区分课程、教学需求和具体待排任务，后续规则会反复返工。需要在第一阶段固定这些概念和数据字典。

### 数据风险

真实学校数据可能存在缺失、重复、隐性规则和资源不足。必须先做 Staging 和预检，不能让求解器承担所有数据错误诊断。

### 算法风险

不能过早追求软约束。先保证可行、可解释和无硬冲突，再优化课表质量。

### 工程风险

同步求解、共享可变对象和覆盖发布版本会导致超时、并发错误和不可追溯。必须采用异步 Job 和不可变版本。

### 产品风险

人工调课体验和冲突解释决定排课员是否愿意使用系统。不能只交付自动排课按钮。

### 许可证风险

必须保持自研代码边界，记录第三方依赖，不复制 GPL/AGPL 项目代码、页面和数据库脚本。

## 16. 后续扩展

第一版稳定后再评估：

- 走班和分层教学
- 拆班和多个教师共同授课
- 请假、代课和临时调课
- 多校区和跨校区移动时间
- 中职实训室、设备和工位
- 学生个人选课
