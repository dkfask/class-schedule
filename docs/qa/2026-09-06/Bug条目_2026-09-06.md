## BUG-1: 教室列表接口 500——room_type 为 NULL 时 NPE

- **严重程度**: S1（核心旁路不可用：基础数据-教室标签完全不可用）
- **状态**: 已验证关闭（修复：item() 改用 HashMap 组装属性；补集成测试 roomListAndDetailTolerateNullRoomType）
- **复验轮次**: 1
- **回归结果**: `GET /api/master-data/rooms → 200`（RAPI roomType=null 正常返回）；浏览器教室标签 4 行正常，RAPI 停用→启用全链路通过（TC-02-03/02-06）
- **发现方式**: 手动执行（浏览器）+ API 复现 + 日志定位
- **复现步骤**:
  1. Planner 登录，进入「基础数据」页
  2. 点击「教室」标签（或直接 GET /api/master-data/rooms?active=false&page=0&size=20）
- **预期行为**: 教室列表正常显示 4 行（含容量列）（依据 TC-02-03）
- **实际行为**: 页面显示"请求失败 (500)"，列表为空
- **证据**: API: `GET /api/master-data/rooms → 500`（稳定复现）；日志: `java.lang.NullPointerException at java.util.Map.of ← MasterDataRepository.item(MasterDataRepository.java:191)`；数据: `room` 表 id=3 RAPI、id=4 RHTTP 的 `room_type` 为 NULL
- **环境**: http://localhost:5173（API :8080）/ planner / ZCode IAB
- **根因分析**: `MasterDataRepository.item()` 用 `Map.of("roomType", rs.getString("room_type"), ...)` 组装教室行属性，`Map.of` 不接受 null 值（E2，MasterDataRepository.java:189-196）；历史 API 测试数据未填教室类型即触发。后端集成测试未覆盖"教室无 room_type"数据形态（推断）
- **影响范围**: 基础数据-教室标签；`/api/master-data/overview`（同经 item() 映射教室→见 BUG-2）；工作台排课条件检查
- **Severity 依据**: 教室管理这一核心旁路整体不可用，且阻断工作台数据读取 → S1
- **修复建议**: `item()` 改用 `HashMap` 允许 null，或对 `room_type`/`student_count` 做 null 兜底（如 `rs.getString(...) ?? ""`）；补充"教室无类型"的集成测试用例
- **回归建议**: TC-02-03、TC-02-06、TC-06-01

## BUG-2: 概览接口 500（双根因叠加）且工作台横幅与就绪状态矛盾

- **严重程度**: S1（工作台数据读取失败、误导性横幅）
- **状态**: 已验证关闭（修复：overview 节次 SQL 按有无 termCode 拆分为两条路径；补集成测试 overviewWorksWithAndWithoutTermCode）
- **复验轮次**: 1
- **回归结果**: `GET /api/master-data/overview → 200`（30 节期/4 教室）；浏览器工作台横幅消失，显示"数据已同步"（TC-06-01）
- **发现方式**: 手动执行（浏览器）+ API 复现 + 日志定位
- **复现步骤**:
  1. Planner 登录进入「排课工作台」
  2. 观察右侧"排课提示"面板（或直接 GET /api/master-data/overview，不带 termCode 参数）
- **预期行为**: 概览正常返回，工作台显示"数据已同步"（依据 TC-06-01）
- **实际行为**: 接口 500；页面显示红色横幅"基础数据暂时无法读取，无法安全开始排课"，但同一面板同时显示"排课条件已就绪：节次 30 · 启用教室 4 · 有效教学需求 6"，且"开始自动排课"按钮可用——横幅文字与实际门控状态矛盾
- **证据**: API: `GET /api/master-data/overview → 500`（3/3 稳定）；日志两条根因：① 同 BUG-1 的 NPE（item:191）；② `BadSqlGrammarException: could not determine data type of parameter $1`——`MasterDataController.overview` 的节次 SQL `WHERE (? IS NULL OR t.code=?)` 在 termCode 为 null 时 PostgreSQL 无法推断 `$1` 类型（E3 日志 2026-09-06T03:46:55Z）；页面截图（工作台横幅）
- **环境**: 同上
- **根因分析**: 双根因叠加——根因 A = BUG-1 的 NPE；根因 B = overview 节次 SQL 的 `? IS NULL` 参数类型推断问题（E2，MasterDataController.java overview 方法）。**与 visual-test-report.md 中 RuleFactRepository 已修复的同类问题（"? IS NULL 参数类型无法推断"）同模式复发**，新代码未套用"无筛选/带筛选拆分 SQL 路径"的既定修法
- **影响范围**: 工作台首屏状态、master-data 概览消费方；不阻塞求解（readiness 独立接口正常）
- **Severity 依据**: 核心入口的数据读取失败 + 误导性告警 → S1
- **修复建议**: 根因 B 按 RuleFactRepository 先例拆分无参数 SQL 路径或显式 `CAST(? AS text)`；根因 A 见 BUG-1；横幅文案与实际门控（readiness）解耦
- **回归建议**: TC-06-01、TC-02-01

## BUG-3: PDF 导出所有中文渲染为问号（CJK 字体缺失）

- **严重程度**: S1（核心导出物对目标用户不可读）
- **状态**: 已验证关闭（修复：镜像安装 fonts-wqy-microhei + compose 注入 APP_PDF_FONT_PATH/NAME；loadFont 加固为"命名查找失败回退首个字体、任何字体失败回退内置字体"，避免字体问题升级为 500）
- **复验轮次**: 2（第 1 轮尝试 Noto CJK 失败——其 .ttc 为 CFF 轮廓，TTFSubsetter 不支持，报"OTF fonts do not have a glyf table"；第 2 轮换文泉驿微米黑通过）
- **回归结果**: 课表 PDF 15KB（字体已嵌入），渲染验证"课表版本 v25"、"英语/语文/数学"等中文全部正常（TC-08-03/04）
- **发现方式**: 手动执行（浏览器下载 + 双渲染器交叉验证）
- **复现步骤**:
  1. 发布任一版本，进入「已发布课表」页
  2. 点击「下载 PDF」（或 GET /api/schedule-versions/{id}/exports/pdf?view=CLASS）
  3. 打开下载的 PDF
- **预期行为**: 中文（课表版本/课程名/教师名）正常显示（依据 TC-08-04）
- **实际行为**: 布局与数据行完整，但所有中文字符均为 `?`（标题"????? v25"、行"?? | T003 | G7-2..."）；校验报告 PDF 同样受影响
- **证据**: 渲染图 `/tmp/v25.pdf.png`（qlmanage）与 `/tmp/v25-page1.png`；PDF 仅 924 字节、无嵌入字体（`/FontFile` 缺失）；`docker-compose.yml` 未设置 `APP_PDF_FONT_PATH/APP_PDF_FONT_NAME`，容器内无 CJK 字体；`application.yml` 对应配置默认空（E2+E4）
- **环境**: 同上
- **根因分析**: PDFBox 导出依赖 `app.pdf.font-path` 提供的 CJK 字体，compose 部署链路未配置，回退字体无法映射中文 → 全部替换为 `?`（E2 推断，待读 SchedulePdfExportService 字体装载段确认行号）
- **影响范围**: 课表 PDF、校验报告 PDF；打印视图（/print）待查
- **Severity 依据**: 面向学校的正式交付物不可读 → S1
- **修复建议**: compose 注入字体文件路径（如 Noto Sans CJK）并在镜像内安装字体；补"中文字形非问号"的渲染级测试（现有 SchedulePdfExportServiceTest 只断言页数与文本存在，未断言字形）
- **回归建议**: TC-08-03、TC-08-04、TC-08-06

## BUG-4: 会话过期后无法到达登录页，用户被困工作台且无提示

- **严重程度**: S2（体验陷阱，无安全/数据后果）
- **状态**: 已验证关闭（修复：App.vue 的 auth:expired 监听中先清除 auth store 的 user 再跳转登录页）
- **复验轮次**: 1
- **回归结果**: 重启 API 使会话失效后访问受保护页，正确落在 /login 且无数据泄漏（TC-01-04）
- **发现方式**: 手动执行（重启 API 使会话失效后操作）
- **复现步骤**:
  1. Planner 登录并停留在任意页面
  2. 重启后端服务（会话失效）
  3. 点击任意数据刷新操作
- **预期行为**: 跳转登录页并给出过期提示（依据 TC-01-04）
- **实际行为**: `auth:expired` 事件正常派发（挂监器实测 8 次），但最终停留在 /workspace，无任何可见提示；此后所有请求静默失败
- **证据**: 浏览器内事件计数 `expiredCount=8`、`path=/workspace`、无错误可见元素（E3）；代码链: `http.ts:49-51` 派发事件 → `App.vue:16` `router.push('/login')` → `router.ts:31` 守卫 `to.path==='/login' && auth.isAuthenticated → '/workspace'`——401 未清除本地 `user` 状态，`isAuthenticated` 仍为 true（E2）
- **环境**: 同上
- **根因分析**: 401 处理只派发事件不清除认证状态；守卫把已认证用户从 /login 弹回
- **影响范围**: 所有需认证页面的过期场景
- **Severity 依据**: 无数据/安全后果，但用户完全失去可操作路径且无提示 → S2
- **修复建议**: `auth:expired` 监听中先清除 auth store 的 user（或强制 `loadMe()` 复核）再跳转登录
- **回归建议**: TC-01-04
