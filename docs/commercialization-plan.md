# 商业化设计方向（后续开发规划）

> 状态：方向确认，尚未进入商业功能开发。本文档补充产品与交付方向，不改变当前单校 MVP 的技术范围，也不代表项目已经具备订阅、支付或多租户 SaaS 能力。

## 1. 当前结论

项目当前最适合的商业路径是：

**单校付费试点 + 实施/部署服务 + 年度软件维护或托管服务。**

首期不直接承诺低价自助 SaaS，也不把系统销售为完整教务平台。先通过真实学校试点验证三件事：

1. 学校真实数据能否稳定导入并完成排课闭环；
2. 排课员是否愿意持续使用人工调整、版本和审计能力；
3. 数据配置、规则适配、培训和运维的实际成本是否支持标准化报价。

多校 SaaS、在线订阅和产品内计费属于后续阶段，必须通过本文档第 8 节的闸门后再立项。

## 2. 首期目标客户

### 适合试点的客户

- 中小学，行政班排课为主；
- 有明确的排课负责人，能够提供教师、班级、课程、教室、作息和教学计划数据；
- 愿意安排一名业务负责人参与规则确认、试排验收和上线培训；
- 首期规则以教师/班级/教室冲突、固定课、连堂、容量和基础可用时间为主；
- 接受单校单实例、受控托管或校内部署方式。

### 暂不适合承诺的客户

- 以走班、分层、复杂合班、跨校区或实训设备排课为核心的学校；
- 要求系统同时覆盖成绩、考勤、收费、家长端、考试或完整教务平台的客户；
- 要求无需数据整理、无需业务确认即可自动生成“最优课表”的客户；
- 要求立即实现多学校统一管理、在线自助开通和自动计费的客户。

## 3. 可售卖的首期产品

### 单校排课试点包

交付一个学校、一个试点学期的受控环境，包含：

- 学校基础数据模板和数据清洗指导；
- 教师、班级、课程、教室、教学需求和作息导入；
- 基础规则配置与数据可行性预检；
- 异步自动排课、候选版本、人工调整、锁定和发布门禁；
- 班级/教师/教室课表查询、导出和打印入口；
- 版本差异、操作审计和已发布版本保护；
- 排课员与只读用户的基础角色；
- 首轮上线培训、试排陪跑和问题清单。

### 年度维护或托管服务

在试点验收后，可按年度提供：

- 版本升级和安全修复；
- 数据备份与恢复协助；
- 运行健康检查和故障响应；
- 每学期导入、规则复核和发布陪跑；
- 使用问题答疑和有限度配置支持。

校内部署、受控云托管和后续升级的责任边界必须在合同中单独写明。

### 超范围服务

以下内容不包含在标准试点包中，应单独评估和报价：

- 复杂合班拆分、分层走班、跨午休或跨校区规则；
- 多教师共同授课、考试排程、临时调课和通知集成；
- 与学校现有教务系统、统一身份平台或消息平台集成；
- 专属报表、专属流程、界面定制或大规模数据治理；
- 多学校 SaaS、组织级管理员和集团报表。

任何超范围承诺都必须先完成数据样本评估和技术可行性确认。

## 4. 首轮报价假设

以下仅是用于首批客户访谈和报价实验的人民币区间，不是已经批准的正式价目表：

| 项目 | 报价假设 | 说明 |
| --- | ---: | --- |
| 单校试点实施包 | ¥20,000–¥50,000/校/学期 | 含数据整理、配置、试排陪跑、培训和一次上线验收 |
| 年度软件维护/托管 | ¥30,000–¥80,000/校/年 | 试点验收后报价，按部署方式、支持级别和规模调整 |
| 私有化部署 | ¥20,000–¥60,000/次 | 含环境初始化、迁移和上线协助，不含云资源费用 |
| 超范围配置/集成 | ¥1,500–¥3,000/人日 | 先评估、后报价，需保留验收标准和变更记录 |

报价不应按“自动生成一张课表”计费，而应围绕学校交付结果计价：数据可用、候选方案可解释、冲突可控、版本可追溯和顺利发布。

首批客户允许折扣，但折扣必须交换可复用资产，例如脱敏数据、书面反馈、案例授权或明确的续费评估时间点。正式定价需由业务负责人根据至少 2 个试点的实施工时、支持工时和客户支付意愿复核。

## 5. 标准销售与交付生命周期

```text
线索筛选
  -> 需求与数据访谈
  -> 规则适配评估
  -> 书面报价与范围确认
  -> 试点合同
  -> 数据清洗与导入
  -> 规则配置与预检
  -> 首轮求解与人工调整
  -> 学校业务验收
  -> 培训和上线
  -> 维护/托管
  -> 学期复盘与续费评估
```

### 关键交付物

| 阶段 | 必须留存的交付物 |
| --- | --- |
| 售前 | 客户画像、数据样本、规则适配清单、范围与报价单 |
| 实施 | 数据导入记录、规则确认单、问题清单、变更记录 |
| 试排 | 求解任务记录、候选版本、未排原因和冲突说明 |
| 验收 | 验收用例、学校负责人签字或书面确认、遗留问题清单 |
| 上线 | 发布版本标识、备份结果、培训记录、支持联系人 |
| 维护 | 健康检查、故障工单、升级记录、学期复盘和续费建议 |

## 6. 合同与服务边界

合同至少应明确：

- 服务对象是一个学校、一个约定学期或年度服务周期；
- 学校负责数据真实性、授权和规则确认；服务方负责系统运行、配置协助和约定范围内的缺陷修复；
- “可发布”以全部教学任务已分配、Hard 约束为零、独立校验通过和学校业务确认共同定义；
- 不承诺任意规则均可自动满足，不承诺固定时长内对所有规模数据求得全局最优；
- 校内部署与云托管的数据库、备份、补丁、监控和故障责任分别归属；
- 数据导出格式、备份保留期、服务终止后的导出窗口和删除方式；
- AI 辅助功能为可选能力，不把外部模型生成内容当作排课事实或发布依据；
- 许可证、第三方依赖、隐私和学校数据处理责任由合同与隐私文件共同约束。

## 7. 试点 Go/No-Go 门槛

签订首个付费试点前，至少完成：

- 一所真实学校或高相似度脱敏数据的端到端导入、求解、手调、发布和导出；
- 规则适配清单，明确已支持、需人工配置和明确不支持的规则；
- 真实规模性能基线：排队时间、首个可行解时间、总时长、不可行率、资源占用；
- 中文 PDF/打印和主要浏览器流程的人工作品验收；
- 备份恢复演练、访问控制复核、生产告警和故障处理流程；
- 应用及基础镜像许可证人工复核；
- 试点合同、验收表、数据处理说明和支持联系人模板。

出现以下任一情况时，不应承诺上线：数据无法解释、核心规则明显超出范围、发布门禁无法通过、没有可恢复备份、责任边界未签字确认，或关键许可证/安全问题未闭合。

## 8. 多校 SaaS 的后续闸门

只有同时满足以下条件，才进入多校 SaaS 立项：

1. 至少 2 个真实学校试点完成验收，并有可复用的实施手册；
2. 记录并复核实施工时、支持工时、求解性能、不可行率和续费意愿；
3. 引入学校/组织租户实体、成员关系、组织管理员和平台管理员边界；
4. 所有主数据、学期、版本、任务、导入批次、审计和导出接口均按租户强制隔离；
5. 完成订阅、套餐、配额、到期、宽限、停服、数据导出和删除的状态设计；
6. 完成支付/账单提供方的合规评估、回调幂等和对账方案；
7. 完成正式 SLA、RPO/RTO、监控告警、灾备演练和客户支持值班方案；
8. 完成隐私、数据处理、许可证和安全评审。

在这些条件完成前，禁止把当前用户级 owner、基础角色或单实例部署描述为多租户隔离和 SaaS 计费能力。

## 9. 后续 90 天方向

### 0–30 天：试点准备

- 固化客户访谈表、规则适配清单、报价单和验收模板；
- 用真实或脱敏中型数据补齐性能、打印、导入和备份证据；
- 完成许可证、安全、生产权限和运行告警的人工复核；
- 选定首个试点客户，不扩大产品承诺范围。

### 31–60 天：交付验证

- 完成一个学期的陪跑试点；
- 记录实施与支持工时、每次失败原因和学校反馈；
- 将重复出现的配置工作整理为模板、检查表或产品需求；
- 形成首版维护服务目录和问题分级规则。

### 61–90 天：商业复盘

- 复盘客户是否愿意为年度维护或托管续费；
- 计算单校交付毛利和可承受支持成本；
- 评估第二个学校是否能复用同一套交付流程；
- 仅在证据充分时决定继续私有化路线，或启动 SaaS 组织/租户设计。

## 10. 首期指标

每个试点至少记录：

- 从签约到首次可行候选的天数；
- 数据清洗、规则配置、培训和支持工时；
- 首个可行解时间、总求解时长和不可行率；
- 发布前人工调整次数和硬冲突数；
- 导入失败率、故障恢复时间和支持工单数量；
- 学校排课员满意度、试点转付费率和年度续费意愿；
- 单校收入、直接交付成本和贡献毛利。

这些指标用于验证商业模式，不用于制造尚未经过真实数据验证的算法或生产承诺。

## 11. 与当前代码状态的关系

当前代码已经支持单校试点所需的主要业务闭环、版本审计、发布门禁、基础角色、导入导出和 Docker 部署路径；但以下能力仍属于发布前或商业化前置工作，而不是已完成的 SaaS 能力：

- 完整用户管理、正式跨用户 RBAC 和审计查询；
- 真实中型学校性能基线、生产告警、Outbox、灾备与正式 RPO/RTO；
- 复杂走班、合班拆分、跨午休和设备排课规则；
- 组织/租户隔离、订阅计费、配额、支付和账单；
- 最终许可证、隐私和数据处理审查。

任何开发任务若要扩大到上述范围，应先更新本规划、明确业务负责人和验收证据，再单独立项。
